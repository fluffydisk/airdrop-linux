# In-app Flatpak updates

Application-source pushes now build and test that exact immutable GitHub commit.
A monotonically increasing build sequence is generated by Actions for internal
ordering, without requiring manual source/revision edits. Users do not see it.
The existing protected production-signing/Pages approval remains required.

Settings > Check for updates retrieves notification-only HTTPS channel metadata
and compares the installed version/build marker. No metadata URL or payload is
executed. Update invokes the official Flatpak CreateUpdateMonitor/Update portal
through an in-sandbox GIO helper. Flatpak selects the calling app's existing
origin, verifies repository/commit signatures and rejects permission increases.
No host execution, filesystem override or signature bypass is introduced.

The UI reports actual portal progress, distinguishes failure/cancellation and
empty transactions, and offers Quit to finish update after success. Reopening
from the desktop launches the updated deployment. Check preserves this finish
notice instead of comparing the still-running old sandbox again.

The previously shipped Flatpak cannot gain this functionality just by pushing
source. It requires a one-time standard Flatpak update after publication. Later
updates can use the in-app control. Older packages without channel provenance
remain managed by the system software manager.

Validation: 115 unit tests passed; native Electron integration passed (tray test
skipped without a StatusNotifier watcher); the compiled C helper passed directed
progress/success/empty/failure checks over real D-Bus with a controlled service.
The protocol fixture is not an actual package installation or proof of a real
interactive desktop consent flow. Existing signed-repository acceptance still
checks real installation/update/migration and signature rejection in Actions.
Full packaged in-app update acceptance must be recorded separately when run.

Official API: https://github.com/flatpak/flatpak/blob/main/data/org.freedesktop.portal.Flatpak.xml

The signing acceptance suite also runs test-installed-update-portal.py against
its actual signed application and served OSTree origin. It exports a changed
payload, checks denied portal consent leaves the installed commit intact, then
allows consent in the disposable CI account and invokes the helper inside the
installed sandbox. Success requires the new commit and new payload in a newly
launched sandbox, plus unchanged data/identity fixtures. Results are recorded in
inapp-update.log; do not call this passed until the Actions result is available.

An initial publication from a superseded run (40721697579) was rejected before
signing because its source workflow was cancelled when newer code arrived.
Candidate 40721695010 then exposed an unrelated order-dependent preservation
fixture: a full mirror could cache a commit through its valid canonical ref
before visiting the intentionally invalid alias. The regression now explicitly
pulls the invalid alias into a fresh repository, retaining GPG and ref-binding
verification. The corrected complete preservation regression passed locally.

Run 40722748893 built and installed the app and passed X11 functional checks,
then caught a real startup/manual-check race under Wayland: manual Check returned
an in-flight status rather than the completed result. Both calls now share one
pending check promise. The regression covers one network operation for concurrent
callers, completed result delivery, subsequent checks and retry after failure.
The original failed log remains in wayland-check-race-failure.log.
